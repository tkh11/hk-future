# Аудит каталога HEISSKRAFT — 30.10.2026

## Вывод

Сильная задержка локального открытия воспроизводится в режиме разработки Next.js. На том же компьютере, с тем же кодом и базой, production-сборка отвечает существенно быстрее: около 0,22–0,23 с вместо 11 с. Это подтверждает значительный вклад режима разработки; конкретный внутренний участок dev-runtime, создающий задержку, отдельно не профилировался.

При этом каталог действительно нуждается в оптимизации: браузер получает оригинальные изображения, опубликованные медиа не кешируются, поиск в шапке требует загрузки всего поискового набора, а разделы выводят все карточки сразу. На мобильной сети эти проблемы сохраняются и в production.

Для текущих 221 опубликованной карточки и 2 619 вариантов увеличение мощности сервера не является первоочередным действием. Сначала следует уменьшить объём работы и передачи данных.

Код приложения, зависимости и записи CMS в ходе аудита не изменялись. Созданы этот отчёт и результаты проверок. Использованы навыки ECC `react-performance` и `security-review`.

## Находки и приоритеты

### P1 — изображения карточек и поиска передаются в исходном размере

`src/sections/products/ProductGrid.tsx:12`, `ProductScreen.tsx:18`, `src/components/layout/SiteSearch.tsx:27`: используется `Image unoptimized`. У Media не настроены `imageSizes` (`src/cms/collections.ts:102`). Указание width/height в JSX резервирует место, но не уменьшает файл.

У 93 карточек основной категории Therm изображения суммарно весят 55,11 МиБ. Multilayer: 24 карточки / 34,50 МиБ; HDPE: 11 / 20,49 МиБ. Даже миниатюра поиска 56×56 получает исходный файл.

**Действия:** создать производные размеры для миниатюр, карточек и страницы товара; передавать правильные `srcset`/`sizes`; сохранить оригиналы отдельно. Начать с реально используемых основных изображений, затем обработать галереи. Делать преобразование при импорте/загрузке или фоновым заданием, а не заново при каждом посещении. Payload поддерживает [imageSizes](https://payloadcms.com/docs/upload/overview).

### P1 — опубликованные файлы запрещено кешировать

`src/proxy.ts:25` устанавливает `Cache-Control: private, no-store` для всех API-ответов, включая опубликованные изображения. Обычный GET опубликованного изображения подтвердил этот заголовок.

**Действия:** разделить политику для закрытых файлов и публичных производных изображений. Закрытые файлы и preview сохраняют проверку доступа и `no-store`. Для публичных версий предусмотреть кеш браузера/CDN, версионированные имена и очистку при снятии публикации. Не снимать защиту со всей медиатеки. Длительный браузерный кеш нельзя мгновенно отозвать: срок хранения должен соответствовать требованиям к снятию материала с публикации.

### P1 — весь каталог и артикулы вариантов загружаются для шапки и повторно для каталога

`src/app/(frontend)/layout.tsx:52`, `src/content/cms-adapter.ts:187`, `:267`, `:274`, `src/sections/catalog/CatalogScreen.tsx:7`.

Шапка ждёт полный поисковый набор, включая все опубликованные товары, артикулы вариантов, статьи и страницы. Для каталога похожая выборка выполняется снова. Последовательная загрузка страниц по 200 записей продолжается до конца коллекции. `React.cache` уменьшает повторы внутри одного рендера, но не является кешем между посещениями. В `enrichVariantSummaries` также есть линейный поиск семейства для каждой карточки и многократное копирование массивов.

**Действия:**

1. Поиск шапки запрашивает только три результата после ввода, с короткой задержкой 150–250 мс и отменой устаревшего запроса.
2. Стартовая страница каталога получает только данные трёх разделов. Внутренний раздел — только свою страницу товаров, например 24 карточки, с устойчивой сортировкой и переходами по страницам.
3. Число вариантов и краткую сводку SKU вычислять отдельно от каждого открытия каталога. Полный список артикулов хранить в серверном поисковом индексе.
4. Кешировать только опубликованные DTO, явно отделив их от авторизованного preview. При публикации, снятии публикации, смене категории и изменениях вариантов обновлять кеш/индекс. Не помещать `requestContext`, cookies и проверку прав в общий кеш.
5. Сохранить начальную серверную выдачу текста, ссылок и первой страницы результатов; поиск и пагинация должны сохранять URL и историю браузера.

На текущем объёме достаточно PostgreSQL и компактного поискового слоя. Отдельный поисковый сервис и Redis следует добавлять по измеренной необходимости.

### P1 перед внешним запуском — ограничить стоимость публичных запросов

Установленный REST-обработчик Payload принимает `limit=0` как отсутствие пагинации. Без авторизации подтверждены ответы на 221 товар и 2 619 вариантов с минимальным набором полей. Максимальная глубина по умолчанию в установленном Payload — 10. В приложении нет общего ограничения частоты публичных чтений; ограничение импортов относится только к импорту.

Это риск перегрузки и массовой выгрузки при доступном API, а не подтверждённая утечка закрытых данных или проведённая атака. Внешняя конфигурация уже требует gateway и закрывает API без его секрета — эту защиту нужно сохранить. Публичный HTML при этом тоже нельзя бесконтрольно заставлять выполнять дорогую полную выборку.

**Действия:** отдельный узкий API поиска/каталога с разрешёнными параметрами, максимальным размером страницы, ограниченной длиной запроса, явными полями, `depth`/`joins`, таймаутами и rate limit на шлюзе. Не открывать весь административный REST API ради поиска. Глубина раскрытия связей влияет на объём и стоимость запроса — см. [Payload Depth](https://payloadcms.com/docs/queries/depth).

### P2 — подтверждённые ошибки интерфейса

1. **Мобильная горизонтальная прокрутка.** На Therm при ширине 390 CSS-пикселей документ расширяется до 430. Причина — длинные слова в заголовках двухколоночных карточек: например, «полипропиленовая», «воздухоотводчиком». У `.card h2` нет подходящего переноса (`src/sections/products/Products.module.css:41`). Нужен перенос длинных слов, затем проверка на 320/360/390/430 px. Скрывать весь overflow страницы вместо устранения причины не следует.
2. **Неверное обозначение способа заказа.** `ProductScreen.tsx:22` безусловно выводит «Изготовление по запросу», а `ProductGrid.tsx:13` выводит его при отсутствии общего SKU. Все 221 опубликованная карточка имеют тип family, SKU находятся в вариантах. Отсутствие SKU у семейства не означает изготовление под заказ. Показ привязать к явному типу/данным, не выдумывая наличие или сроки.
3. **Лишняя работа на карточке товара.** `getProductContent` не обёрнут в request-scoped `cache`, но вызывается и из `generateMetadata`, и из страницы (`src/app/(frontend)/products/[slug]/page.tsx`). Варианты HMV — 208 строк — все передаются и выводятся сразу. Дедуплицировать чтение товара; таблицу разбивать на страницы/порции с сохранением поиска и доступности.
4. **Лишнее чтение всех родителей.** Access-функция вариантов каждый раз получает все опубликованные товары (`src/cms/catalog-fields.ts:72`). При дальнейшем росте заменить на проверку нужных родителей или эквивалентное условие в БД, сохранив запрет доступа к вариантам закрытых товаров.
5. **Конкурентная публикация одинаковых SKU.** Сейчас уникальность вариантов проверяется запросом `count`, а индекс SKU не уникальный (`src/cms/catalog-fields.ts:86`). Две параллельные публикации могут пройти проверку одновременно. Подтверждённого дубля в опубликованных данных сейчас нет. Нужна защита на уровне БД, например частичный уникальный индекс для опубликованных SKU, позволяющий сохранять конфликтующие черновики.

### P2 — зависимости и безопасность

Свежий `npm audit --omit=dev` сообщил 10 затронутых пакетов: 3 high и 7 low. Это цепочки двух advisories, а не десять независимых дыр.

- **graphql-scalars:** npm связывает high с [GHSA-x8rm-f576-gq67](https://github.com/advisories/GHSA-x8rm-f576-gq67). В проекте стоит 1.22.2. Проверенный файл содержит ограниченное выражение `^\+[1-9]\d{6,14}$`; подробное описание advisory указывает, что проблема появилась в 1.24.1. Поэтому этот конкретный ReDoS не подтверждается для установленного кода, несмотря на широкий диапазон npm. Дополнительно GraphQL отключён и `/api/graphql` возвращает 404. Зафиксировать обоснованное исключение, не выполнять слепое принудительное обновление.
- **deepmerge 4.3.1:** [GHSA-gcqx-w48m-w2h4](https://github.com/advisories/GHSA-gcqx-w48m-w2h4), low, применимый диапазон установленной транзитивной зависимости Payload. В advisory исправленная версия не указана. Путь эксплуатации в этом приложении не доказан. Проверить использование с недоверенными объектами, следить за исправлением Payload/зависимости, сохранить валидацию и ограничения административного доступа. Не откатывать Payload на старую несовместимую версию по автоматическому предложению npm.

## Правила оптимизации контента

Целевые размеры ниже — стартовые бюджеты, а не уже достигнутый результат. Для технических чертежей главным критерием остаётся читаемость размеров и подписей.

| Контент | Рекомендуемая подготовка |
| --- | --- |
| Миниатюры поиска | 112–160 px для Retina; ориентир 10–30 КБ; отдельный файл, не оригинал |
| Карточки товаров | Несколько размеров примерно 320/640/960 px, WebP и при необходимости AVIF; ориентир 50–150 КБ на типовое изображение |
| Основное фото товара | До 1 200–1 600 px для стандартного просмотра; оригинал — по явному открытию; ориентир 150–350 КБ с визуальной проверкой |
| Чертежи | Отдельный тип материала; PNG или WebP без потерь там, где обычное сжатие портит подписи; полноразмерная версия по нажатию |
| Галереи | Миниатюры и отложенная загрузка полноразмерных кадров; исключать случайные дубли основного фото |
| Видео обложек | Подготовить облегчённые версии под реальный размер карточки, постер, совместимый MP4; сохранить длительность, петлю и остановку вне экрана; необязательные кодеки — только с fallback |
| PDF | Оптимизированная экранная копия, текстовый слой и небольшой preview; показывать размер скачивания; оригинал хранить отдельно; не подгружать PDF автоматически |
| Данные товара | Одно семейство и связанные варианты; отдельные числовые характеристики/единицы; короткое описание; роль и порядок каждого медиафайла |
| Поисковый индекс | Название, SKU вариантов, серия, категория, синонимы; без галерей, PDF, полного описания и служебных полей |

Уже есть полезная основа: изображения/документы связаны через медиатеку, PDF дедуплицируются по хешу, конфликтные записи не публикуются. Не удалять исходники и черновики ради уменьшения веса страницы: они не являются автоматически загружаемым публичным контентом.

Обработку 1 147 файлов следует выполнять возобновляемыми пакетами с отчётом ошибок. Использовать существующие ID и связи, не менять адреса товаров. Перед массовым преобразованием — резервная копия БД и файлов; после — проверка ссылок, статусов доступа и визуального качества.

## Рекомендуемый порядок работ
