# Payload CMS: среды, публикация и восстановление

CMS дополняет существующий сайт. GitHub Pages остаётся статическим демо со
снимком локального контента; административная панель, API и новая продукция CMS
там не работают. Подключение production-хостинга и внешних учётных записей
не выполнено: для этого нужны выбранные сервисы и доступы владельца.
Работа с контентом описана в [инструкции редактора](cms-editor-guide.md).

## Среды

| Среда | Назначение | Данные и доступ |
|---|---|---|
| Локальная | Разработка и обучение редактора | Изолированный PostgreSQL, приватные `.local/uploads`; отдельные локальные секреты |
| Staging в РФ | Проверка редакторского процесса и миграций | Отдельные БД, S3-префикс/бакет, секреты и учётные записи; доступ через VPN/MFA-шлюз |
| Production в РФ | Публичный сайт и опубликованные материалы | Node.js-приложение, PostgreSQL, приватный S3; отдельные резервные копии |
| GitHub Pages | Демонстрация фронтенда | Только существующий локальный контент и публичные статические ресурсы |

Используйте Node из `.nvmrc`, npm из `packageManager`, `npm ci` и одинаковые
версии Payload-пакетов. Не включайте schema push в рабочей БД: изменения схемы
проходят через проверенные миграции. Миграции выполняет один процесс до старта
новой версии приложения; запускать их одновременно из нескольких реплик нельзя.

Локально: `npm run cms:local:init`, затем `npm run cms:migrate`,
`npm run cms:bootstrap`, `npm run cms:seed`, `npm run dev`.
Инициализатор использует PostgreSQL 17, установленный отдельно; `PG_BIN`
указывает каталог PostgreSQL CLI, если он отсутствует в PATH.
Исходные каталог, статьи, контакты и тексты решений переносятся seed-командой
без перезаписи уже отредактированных записей.

### Изолированный Docker Compose

`compose.local.yml` — альтернативная локальная среда с PostgreSQL 17.11 и
приватным томом загрузок. Она не использует нативную БД на порту 5433:
приложение доступно только на `http://localhost:3200`, PostgreSQL — только на
`127.0.0.1:55433`. Нужны Docker Engine/Desktop и Compose v2. Docker отсутствовал
на рабочей машине при подготовке: конфигурация проверена статически, запуск
контейнеров и сборка Docker-образа здесь не выполнены.

```sh
node scripts/cms/compose-init.mjs
docker compose --env-file .local/compose.env -f compose.local.yml build app operations
docker compose --env-file .local/compose.env -f compose.local.yml up -d postgres
docker compose --env-file .local/compose.env -f compose.local.yml run --rm operations npm run cms:migrate
docker compose --env-file .local/compose.env -f compose.local.yml run --rm operations node --import tsx scripts/cms/bootstrap.ts
docker compose --env-file .local/compose.env -f compose.local.yml run --rm operations node --import tsx scripts/cms/seed.ts
docker compose --env-file .local/compose.env -f compose.local.yml up -d app
```

Инициализатор создаёт `.local/compose.env` с правами `0600` и случайными
секретами, включая первоначальный пароль администратора. Повторный запуск
не перезаписывает секреты. Для остановки используйте `docker compose` с теми же
аргументами и `stop`; тома данных сохраняются. Команда `down --volumes` удаляет
данные и не входит в процедуру обновления. Параметр `--env-file` обязателен во
всех командах, поскольку Compose берёт из него значения подстановок.

Dockerfile собирает сервер с включённой CMS и недоступной тестовой БД:
публичный контент читается во время запроса. Production-секреты не нужны при
сборке и не копируются в образ. Цель `runtime` содержит рабочие зависимости,
цель `operations` дополнительно сохраняет CLI для миграций и seed. Миграции
выполняются отдельной командой, до запуска новой версии приложения.
Локальный Compose передаёт обеим целям несекретный build argument
`NEXT_PUBLIC_SITE_URL=http://localhost:3200`, совпадающий с `CMS_SERVER_URL`.

Теги [Node 24.22.1](https://github.com/docker-library/official-images/blob/master/library/node)
и [PostgreSQL 17.11](https://github.com/docker-library/official-images/blob/master/library/postgres)
проверены по официальным манифестам 26 октября 2026 года. Перед выпуском
зафиксируйте digest проверенных образов в своём реестре. MinIO не включён:
его [публичный репозиторий](https://github.com/minio/minio) архивирован и больше
не поддерживается. Для проверки S3 используйте отдельный приватный бакет
выбранного поставщика; для локальной разработки достаточно приватного тома.

### Сервер в РФ

`compose.server.yml` описывает запуск образов на уже подготовленном сервере;
`deploy/server.env.example` перечисляет серверные параметры PostgreSQL,
приватного S3 и шлюза. Создайте файл `.local/server.env` с правами `0600` через
менеджер секретов. Замените **все** заглушки, задайте отдельные адреса и секреты
для staging и production, настройте проверку сертификата БД под выбранного
поставщика. Секреты не передаются через Docker build arguments.

Перед сборкой задайте **публичный HTTPS origin конкретной среды**, в точности
равный `CMS_SERVER_URL` и `NEXT_PUBLIC_SITE_URL` из её `.local/server.env`,
без пути и завершающего `/`. Это несекретное значение. В примере ниже замените
заглушку реальным адресом; секреты БД, S3 и шлюза сборке не передаются:

```sh
CMS_PUBLIC_ORIGIN='https://REPLACE_WITH_THIS_ENVIRONMENT_HOST'
docker build --target runtime --build-arg NEXT_PUBLIC_SITE_URL="$CMS_PUBLIC_ORIGIN" --tag heisskraft-cms-runtime:release .
docker build --target operations --build-arg NEXT_PUBLIC_SITE_URL="$CMS_PUBLIC_ORIGIN" --tag heisskraft-cms-operations:release .
```

Next встраивает `NEXT_PUBLIC_SITE_URL` в canonical URLs и карту сайта при
сборке. Одного изменения переменной в запущенном контейнере недостаточно:
для другого публичного адреса образ нужно пересобрать. Значение Dockerfile
по умолчанию (`http://localhost:3200`) предназначено только для локального
Compose. Production и staging должны получать свой явно переданный аргумент;
образ со staging-адресом не переносится в production без пересборки.

Соберите обе цели из одного проверенного commit, опубликуйте их в реестре
организации и задайте `CMS_IMAGE` и `CMS_OPERATIONS_IMAGE` как
`registry/repository@sha256:...` для нужной среды. Серверный Compose использует
эти готовые образы, сам их не собирает. Сначала выполните миграции одним процессом:

```sh
docker compose -f compose.server.yml run --rm operations npm run cms:migrate
docker compose -f compose.server.yml up -d app
```

Для первого запуска после миграций и перед `up` выполните bootstrap и seed
аналогично локальному примеру; `CMS_BOOTSTRAP_EMAIL` и
`CMS_BOOTSTRAP_PASSWORD` передайте только процессу bootstrap через секреты
оператора (`run -e CMS_BOOTSTRAP_EMAIL -e CMS_BOOTSTRAP_PASSWORD`). Само
приложение эти параметры не получает. PostgreSQL и S3 не создаются Compose;
на них должны быть проверены права и сетевые ограничения. Веб-порт открыт
только на loopback, к нему подключается подготовленный HTTPS reverse proxy.
DNS, TLS, MFA/VPN-шлюз, секреты, серверы и внешние резервные копии требуют
настройки инфраструктуры владельцем; эти шаги пока не выполнены.

## Настройки и границы безопасности

- `CMS_ENABLED=true` включает серверный режим. `DATABASE_URL` и случайный
  `PAYLOAD_SECRET` не короче 32 символов передаются через секреты окружения.
  `.env.local`, резервные копии и `.local/admin-access.txt` не коммитятся.
- `CMS_SERVER_URL` — HTTPS-адрес конкретной среды. Не используйте production
  базу или секреты для preview-развёртываний pull request.
- На внешнем сервере требуются `CMS_GATEWAY_SECRET` не короче 32 символов
  и приватное S3-хранилище с HTTPS endpoint и действующими ключами:
  `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_PREFIX`, `S3_ACCESS_KEY_ID`,
  `S3_SECRET_ACCESS_KEY`. S3-учётная запись имеет доступ только к своей среде.
- Закройте административные, preview и изменяющие API-запросы VPN/MFA-шлюзом.
  Приложение не заменяет этот шлюз и не заявляет собственную реализацию MFA.
  Шлюз удаляет одноимённый заголовок от клиента и добавляет проверенный секрет
  сам; обход шлюза по IP/внутреннему порту закрыт firewall. Заголовок и маршрут
  должны соответствовать действующему `src/proxy.ts`: для `/admin/*` и
  `/api/*` используется `x-heisskraft-gateway`. Публичные GET/HEAD файлов
  `/api/media/file/<имя>` пропускаются к проверке доступа Payload без секрета
  шлюза; остальные API-запросы требуют его. Шлюз должен сохранять корректный
  `Origin` у изменяющих запросов.
- Бакет не публичный. Доступ к файлу выдаёт Payload с проверкой прав и статуса
  публикации; анонимный пользователь не должен получать черновые вложения.
  Не помещайте корпоративные документы 1С/HEISSKRAFT OS в публичную CMS.
- Проверяйте роли администратора, редактора и публикующего пользователя.
  Cookies preview без текущей авторизованной сессии не дают прав на черновики.
- SMTP пока не подключён. Восстановление пароля по почте возвращает одинаковый
  ответ 503 для любого адреса, до поиска пользователя и создания токена.
  Явно отключённый почтовый адаптер не выводит письма и ссылки сброса в журналы.
  При утрате пароля обратитесь к администратору. Включение восстановления требует
  настройки реального адаптера доставки и удаления запрета `disableEmailRecovery`.
- Редактор сохраняет изменения коллекций только через настоящий режим
  `draft=true`. Обычное обновление, массовая запись и восстановление версии
  не могут изменить или снять с публикации публичную запись от его имени.
  Произвольный флаг в теле запроса или context не заменяет режим операции.
  Публикующий пользователь выпускает материалы; контакты, решения и навигацию
  меняют публикующий пользователь и администратор. Настройки сайта и роли
  пользователей меняет только администратор. Аналитик видит публичный контент
  и агрегаты, без черновиков и истории настроек.
- Байты медиафайла неизменяемы после создания записи, в том числе для
  администратора. Для замены загрузите новую запись, опубликуйте её и измените
  ссылку на файл в черновике материала. Название и альтернативный текст можно
  редактировать без замены файла. Обработка изображения внутри CMS отключена:
  обрезанный или изменённый файл загружается отдельно. Это сохраняет прежний
  опубликованный файл, пока новая редакция проходит проверку.
- Метрика включается только после задания `METRIKA_ENABLED=true` и номера
  `METRIKA_COUNTER_ID`. `METRIKA_READ_TOKEN` — серверный секрет. Не передавайте
  в аналитику поля формы, адреса электронной почты, телефоны, поисковые строки
  или содержимое документов. Форма пока демонстрационная: событие завершения
  не подтверждает доставку обращения.

Критичные меры на площадке: HTTPS, закрытые порты БД и S3, обновления ОС,
ограничение запросов на шлюзе, мониторинг ошибок и резервного копирования,
контроль свободного места, оповещение ответственного. Публичный сайт не получает
прямое подключение к базе 1С. Ни GitHub Actions, ни эта конфигурация не создают
production-сервер автоматически.

## Проверки и выпуск

`node scripts/cms/test-access.mjs` проверяет права через реальный Local API с
`overrideAccess:false`, на новой локальной БД после применения миграций; после
теста удаляется только созданная им БД. На 26 октября 2026 года прошли все
16 сценариев, включая публикацию, массовое изменение, вложенные категории,
восстановление версий, повышение роли, историю глобальных настроек и сохранение
байтов опубликованного файла при редактировании метаданных и попытках замены,
а также отказ восстановления пароля без создания токена, пока SMTP не настроен,
и видимость владельца блокировки по ID без доступа к чужой учётной записи.
Эта проверка использует локальное файловое хранилище. Проверка внешнего S3,
MFA/VPN-шлюза и полного редакторского процесса на staging остаётся невыполненной:
для неё ещё нужны выделенные среды, учётные записи и настройки инфраструктуры.

Отдельный профиль `playwright.cms.config.ts` проверен на локальной production-
сборке: 26 сценариев REST/браузера (по 13 для экранов 1440×900 и 390×844) прошли.
Проверяются новые адреса товара, вложенной категории и статьи без пересборки, публикация и снятие с публикации
в карточке, поиске и sitemap, недоступность черновых файлов, неизменность
опубликованных байтов, отключённая публикация у редактора, автосохранение,
скрытие и порядок блоков, а также отказ в preview без текущей авторизации.
Новые сценарии проверяют вкладки товара и ручной адрес без смены SKU,
обычные поля текстов решений и восстановление версии, отказ сохранения и
повторную попытку, первую загрузку файла и конфликт двух редакторов.
Команда `test:cms:e2e` создаёт отдельную БД `hk_test_admin_<random>`, папку
загрузок в системном временном каталоге и одноразового администратора. Рабочую
БД и `.local/uploads` она не использует. При завершении очищаются только ресурсы
этого запуска, включая отдельный сервер. Порт 3100 перед запуском должен быть свободен.

Для повторения сначала соберите CMS с `CMS_ENABLED=true`,
`CMS_SERVER_URL=http://localhost:3100`, `NEXT_PUBLIC_SITE_URL=http://localhost:3100`
через `npm run build:production`. Затем выполните
`PLAYWRIGHT_CHANNEL=chrome npm run test:cms:e2e`. Прямой запуск Playwright без
изолированного окружения запрещён конфигурацией. При установленном Chromium
Playwright переменную `PLAYWRIGHT_CHANNEL` можно не задавать.

`CMS_UPLOAD_DIR` — необязательный доверенный абсолютный путь локального хранилища
на сервере, используемый изолированным тестовым процессом. Обычная среда без этой
настройки продолжает использовать `.local/uploads`; S3 в тестах отключён.
Ни поле документа, ни REST-параметр не могут задавать этот путь.

CI разделён на независимые рабочие каталоги: качество, обычная сборка с E2E,
статический экспорт с E2E и CMS с временным PostgreSQL. CMS-задание выполняет
миграции, bootstrap тестового администратора, seed, интеграционные проверки,
серверную сборку, CMS E2E в Chromium и проверку резервной копии. E2E запускается
против отдельного локального production-сервера на порту 3100; сервер
останавливается перед backup. CMS-профиль не записывает traces, видео и
скриншоты, а это CI-задание не публикует отчёты, логи или копии как artifacts.
Учётные данные этого задания
одноразовые и не используются вне CI; PR не получает секреты окружений и права
публикации. GitHub Pages публикуется из main только после всех проверок.

`npm run build:export` создаёт временную копию проекта. В ней отключаются CMS
и аналитика, удаляются административные/API-маршруты, proxy и новые динамические
страницы. Каталог и статьи используют локальные static params. Рабочий `.next`
и исходники при этом не переписываются. Это намеренно не экспорт живой CMS.
Во временной копии CMS-клиент заменяется типизированной заглушкой, которая
останавливает обращение к CMS: выключенного флага окружения недостаточно,
поскольку сборщик заранее обходит динамические импорты. Карта сайта только
в этой копии помечается статической.

Локальная проверка 26 октября 2026 года: `build:export` собрал 49 статических
страниц; `test:assets` проверил все 49 HTML-файлов. Базовые Playwright-сценарии
экспорта в установленном Chrome прошли: 77 успешных, 1 штатный пропуск
desktop-версии теста мобильной раскладки. Экспорт обслуживался на отдельном
loopback-порту 3102; работающий CMS-сервер на 3100 не изменялся. Это результат
локального прогона, не подтверждение выполнения GitHub Actions.

Перед серверным выпуском: резервная копия → миграции → сборка → staging smoke
(публикация, снятие с публикации, preview, импорт, загрузка файлов) → выпуск.
При неудачной миграции сначала остановите записи и установите состояние БД;
не запускайте автоматический откат схемы поверх новых редакторских данных.
Обратная совместимость миграций или восстановление проверенной копии должны
быть предусмотрены до выпуска. Записывайте версию кода, миграцию и время копии.

## Резервная копия

Скрипты требуют PostgreSQL CLI не старее версии сервера. По умолчанию файлы
попадают в `.local/backups` с правами только владельца. Каталог должен лежать
на зашифрованном носителе; сам скрипт не реализует шифрование или перенос
на вторую площадку. Внешний backup-agent хранит независимую приватную копию
в РФ, с собственной учётной записью и политикой хранения. Не открывайте копии
через веб-сервер и не публикуйте их как CI artifacts.

1. Остановите CMS-процесс и все задания, изменяющие данные, либо обеспечьте
   проверенный режим обслуживания с запретом записей. Одна переменная окружения
   не блокирует пользователей — она только подтверждает выполненную остановку.
2. При локальном хранении проверьте `.local/uploads`. При S3 остановите изменения
   бакета и экспортируйте **весь используемый префикс**, включая старые файлы,
   в приватный каталог. В нём файлы лежат относительно префикса, без лишней
   папки `heisskraft/`. Укажите этот каталог через `CMS_BACKUP_UPLOAD_DIR`.
   S3 versioning полезен, но сам по себе не заменяет независимую копию.
3. Выполните:

```sh
CMS_WRITES_PAUSED=true node --env-file=.env.local scripts/cms/backup.mjs
```

Для S3 добавьте `CMS_BACKUP_UPLOAD_DIR=/private/path/to/export`. Для другого
места хранения задайте `CMS_BACKUP_DIR=/private/path/to/backups`.
Скрипт создаёт custom-format `pg_dump`, копию файлов и manifest с SHA-256,
размерами и количеством записей основных таблиц. Отсутствующие медиа,
меняющиеся файлы, неверная БД или ошибка pg_dump не создают завершённую копию.
Пароли и данные документов в manifest и логи не записываются. При S3 без
полного экспортированного каталога скрипт останавливается.

4. Проверьте завершённую копию, затем возобновите работу CMS. Копирование
   шифрованного набора на вторую площадку и мониторинг успеха настраиваются
   отдельно. Предварительная политика: ежедневные копии 14 дней и еженедельные
   8 недель; окончательная политика зависит от согласованных RPO/RTO.

Копия не содержит секретов окружения, ключей шифрования, PostgreSQL-ролей,
настроек gateway и DNS. Они хранятся отдельно в защищённом менеджере секретов
и эксплуатационной документации. Без них полное восстановление среды невозможно.

## Проверка восстановления

Нужна новая локальная БД вида `heisskraft_restore_<suffix>` и пользователь с
правом её создать. Значение `DATABASE_URL` никогда не используется как цель
восстановления. В `CMS_RESTORE_DATABASE_URL` указывается отдельный URL;
пароль берите из менеджера секретов, не сохраняйте команду с ним в историю shell.

```sh
node --env-file=.env.local scripts/cms/restore-check.mjs
```

Предварительно задайте `CMS_RESTORE_DATABASE_URL` в окружении. Можно указать
`CMS_BACKUP_PATH` на конкретную копию; иначе выбирается последняя завершённая.
Скрипт проверяет manifest, контрольные суммы и безопасные пути **до** создания
БД, запрещает удалённый хост, существующую БД и имя исходной базы. Он не
использует `DROP`, `--clean` или перезапись рабочей базы. Затем восстанавливает
дамп, сравнивает количество записей и копирует проверенные файлы в
`.local/restore-checks/<имя-базы>/uploads`.

Тестовая БД остаётся для ручной проверки приложения; автоматического удаления
нет. Это проверка восстанавливаемости данных, а не измерение аварийного RTO:
отдельно запустите CMS на восстановленной базе, проверьте вход, публикации,
товар, черновой файл и PDF, затем зафиксируйте время восстановления.
Регулярно повторяйте упражнение, особенно после обновлений схемы и хранилища.

### Повторное начальное наполнение

Категории, статьи и три исходные страницы получают приватный постоянный ключ
источника. Повторный `cms:seed` ищет запись по этому ключу и сохраняет её новые
адрес, название, статус и ожидающие публикации черновики. Пустая навигация,
сохранённая редактором, также сохраняется. Миграция `seed_source_keys` один раз
связывает исходные записи существующей базы по первоначальным адресам; после
этого URL больше не служит идентификатором наполнения.

Удалённые исходные записи seed создаёт снова. Для временного удаления с сайта
снимайте запись с публикации; после намеренного окончательного удаления
не запускайте seed как обычную операцию выпуска. Новые пользовательские записи
начальное наполнение не изменяет.
