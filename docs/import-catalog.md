# Импорт технического каталога

Импорт создаёт или обновляет **черновики** товаров, не публикует их и никогда не удаляет товары, отсутствующие в файле. Картинки, документы и SEO-поля в первой версии не импортируются. Существующие ручные изменения сохраняются: каждое изменяемое поле нужно отдельно подтвердить в предпросмотре.

## Файлы и шаблоны

Поддерживаются CSV UTF-8 с запятой или точкой с запятой и XLSX с одним видимым листом. Первая строка — заголовки. Лимиты: 5 МБ на файл, 1000 строк товаров, 80 колонок, 20 характеристик, 8000 символов на ячейку. Архив XLSX дополнительно проверяется до ExcelJS: максимум 20 МБ фактически распакованных данных, 100 записей и коэффициент сжатия 200. Формулы, внешние ссылки, макросы, встроенные медиа и чрезмерное оформление не допускаются.

Обязательные колонки: `sku`, `slug`, `title`, `category`, `series`. Необязательные: `externalId`, `description`. Ключи колонок чувствительны к регистру. SKU и внешний идентификатор в XLSX должны иметь **текстовый** тип для сохранения ведущих нулей. Slug содержит строчные латинские буквы и цифры, разделённые одиночными дефисами. Категория и серия задаются стабильным slug/путём; импорт не создаёт их автоматически.

Характеристики задаются колонками `attr:<key>:<type>:<unit>:<label>`. Тип — `text`, `number` или `boolean`. Например: `attr:diameter:number:mm:Диаметр`, `attr:inline:boolean::Ин-лайн`. Для чисел допускаются десятичная точка и запятая без разделителя тысяч; единица измерения указывается в заголовке. Логические значения: `true/false`, `1/0`, `да/нет`. Пустая характеристика не добавляется.

Создать шаблоны с явно учебными строками:

```sh
npx tsx scripts/cms-import-template.ts pipes /tmp/pipes.xlsx
npx tsx scripts/cms-import-template.ts pumps /tmp/pumps.csv
```

Скрипт отказывается перезаписывать существующий файл. Учебные категории и серии нужно заменить на реально заведённые в CMS. Строки `SAMPLE-*` не являются данными каталога и не должны автоматически попадать в seed.

## Подтверждение и конфликтующие изменения

1. Сервер разбирает файл и сохраняет неизменяемый предпросмотр с его SHA-256, различиями и ревизиями товаров.
2. Пользователь видит создаваемые товары, конфликты и ошибки. Ошибки блокируют весь пакет, частичного применения нет.
3. Для имеющихся товаров по умолчанию не меняется ничего. Пользователь отмечает нужные поля для каждой строки. Если меняются и категория, и серия, подтверждать нужно обе связи вместе.
4. Применение принимает только ID сохранённого пакета и выбранные поля. Клиент не передаёт данные товаров для записи.
5. Внутри транзакции повторно проверяются идентичность товара, ревизия последнего черновика, уникальность slug и связи. Изменившийся после предпросмотра товар требует нового предпросмотра. Ошибка отменяет весь пакет.

SKU — основной стабильный ключ, `externalId` — дополнительный. Если они указывают на разные товары или новый внешний ID пытаются привязать к уже существующему SKU, импорт останавливается: сначала согласуйте идентичность товара в CMS. Повторная отправка уже применённого пакета возвращает исходный результат. Повторный импорт файла не создаёт дубликатов.

Пустое описание и пустой список характеристик остаются предложенными значениями. Они очищают соответствующее поле существующего товара только при явном подтверждении. Выбор поля `attributes` заменяет весь список характеристик; интерфейс должен показывать полный список до и после. Прочие поля и медиа не затрагиваются.

## Серверный контракт

Модуль `src/cms/import` предоставляет `parseCatalogImport`, `createImportPreview` и `applyImportPreview`. Все операции предназначены для сервера. `CatalogImportRepository` — адаптер к Payload/PostgreSQL. `actorId` должен поступать из проверенной серверной сессии, а не из тела запроса. Применить пакет может только создавший его пользователь с актуальным правом импорта.

Адаптер обязан:

- Выполнять `transaction` на реальной транзакции БД; исключение откатывает товары и статус пакета.
- Сериализовать импорты через `lockCatalog`, блокировать строку пакета в `getBatchForUpdate` и проверять ревизии товаров атомарно в `updateDraftProduct`. Простая проверка даты до обычного `update` не защищает от гонки с редактором.
- Возвращать актуальный черновик, нормализованные связи и характеристики без служебных `id`. Учитывать последнюю draft-версию в `updatedAt`.
- Сохранять изменения только в черновиках, включая товары с опубликованной версией; публичная версия не меняется до отдельной публикации.
- Защищать уникальность SKU, `externalId` и slug ограничениями БД. Пустой `externalId` нормализовать в `null`, а не в общую пустую строку.
- Запретить прямую запись/изменение снимка предпросмотра из клиентского REST/GraphQL. Пакеты содержат внутренние данные каталога и не должны быть публично читаемыми.
- Ограничить размер HTTP-запроса **до** вызова `formData()`/буферизации, проверить роль, CSRF/origin и лимит частоты до распаковки. Временные исходные файлы не сохранять в публичных media.

Коды `stale-preview` и `identity-conflict` требуют пересоздания предпросмотра/устранения конфликта; `invalid-overwrite` — изменения выбранных полей. Пользовательские ошибки не должны включать стек или ошибки SQL. Поведение отката и CAS проверяется unit-тестами через тестовый transactional repository; адаптер к PostgreSQL дополнительно требует интеграционного теста реальной конкуренции.
