# Правила разработки программы подбора

[Контекст и план](README.md) · [Данные для локальных расчётов](hip32-ssvf-fixture.json)

## Границы первой версии

- Работать в `hk-pump-selection` на ветке `codex/pump-selection`. Перед изменениями проверить рабочую папку, ветку и локальные правки. Изменения в основной ветке и запуск интеграции на сайте — отдельные этапы.
- Начать с девяти артикулов HIP 32 SSVF. Порядок работы: чистая функция расчёта → тесты → интерфейс на тестовых данных → интеграция с Payload → лист данных. Сначала проверить каждую модель, затем оставить до двух ближайших по напору характеристик в каждом ряду. Открывается первая подходящая модель. Сортировка таблицы сохраняет состав выдачи.
- Редактировать инженерные данные через существующие поля Studio. Любое расширение схемы, новая библиотека, серверный сервис или изменение контракта каталога требуют конкретной причины и плана проверки.

## Расчёт и источники данных

- Хранить расчёт отдельно от React, Payload и формата отчёта. Принимать типизированные значения и возвращать типизированный результат с причиной: достаточный или недостаточный напор, расход вне рабочей зоны, неполные данные либо некорректный ввод. Различать неподходящую модель и модель, для которой расчёт невозможен.
- Расход хранить в м³/ч, напор и NPSHr в метрах, P2 в кВт, КПД в процентах. На границе формы принимать десятичную запятую и точку, проверять числа целиком и отклонять пустые, отрицательные и нечисловые значения в полях, где они недопустимы. Округлять при отображении. Сравнение напоров выполнять на расчётных значениях, с явно оговорённым допуском, если он нужен.
- Использовать Q–H из `pump-selection-records.curve.points`. Пределы рабочей зоны брать из той же записи подбора. Расчётный расход должен удовлетворять `Qmin < Qрасч ≤ Qmax`. Напор насоса на этом расходе должен быть не ниже полного требуемого напора; точное равенство допускается. Фактическая точка должна быть единственной, обеспечивать расчётный расход и находиться в пересечении полного рабочего диапазона и интервала исходных данных. Ограничение избытка напора не вводить. Не заменять Q–H оцифрованными границами из каталога и не продолжать кривую за имеющиеся точки.
- Переиспользовать существующую PCHIP-интерполяцию. SVG и числовой результат должны вычисляться по одним сегментам. В узле возвращать исходное значение. Учитывать строго возрастающий Q. При вычислении нескольких показателей проверять диапазон каждого ряда независимо.
- Хранить КПД и NPSHr независимыми рядами. P2 в кВт вычислять по `ρ × g × Q × H / (3 600 000 × η)` для положительных расхода и КПД, в пределах данных обеих кривых. Плотность брать для выбранной среды, КПД подставлять долей единицы. Проверять запас мощности в фактической точке по [правилам подбора](README.md#правила-подбора). Для допуска нужны рассчитанная P2 и номинал двигателя. Пропуск хранить как `null`. Каталожные цифры указывать как оцифрованные. Расхождения с паспортом фиксировать на этапе проверки данных.
- В быстром подборе расчётный напор — полный напор `Hрасч = Hстат + kQрасч²`. Статический напор по умолчанию равен нулю и должен быть в пределах `0…Hрасч`. Коэффициент `k = (Hрасч − Hстат)/Qрасч²`; введённый Hрасч передавать в отбор, расчётную точку и `createSystemCurve` без прибавления Hстат. Режим «Расширенный подбор» пока содержит пустой блок. Интерполировать КПД на расходе в фактической точке в пределах собственного ряда данных. Не объявлять модель инженерно утверждённой по результату проверки только Q и H.

## Код и производительность

- Сохранять существующий стек Next.js, React, TypeScript и Payload. Перед изменением маршрутов, кэширования или границы сервер/клиент читать документацию установленной версии Next.js в `node_modules/next/dist/docs/`.
- Делать изменение минимальным и проверяемым. Расчёт не должен читать БД, форматировать UI или создавать PDF. Компоненты отображают результат, серверный слой загружает и валидирует данные. Один источник логики для интерфейса и отчёта. Общие компоненты выделять, когда появляется реальное повторное использование.
- Оставлять серверными загрузку данных, проверку прав и формирование публичной модели. Клиентскому компоненту передавать параметры и кривые, нужные конкретному экрану. Не импортировать Payload, PDF, Excel или CMS-адаптер в клиентский модуль.
- Загружать все опубликованные записи подбора пакетно. Семейства, ряды и исполнения брать из управляемых Studio групп; не ограничивать выборку списками артикулов в коде. Указывать `select`, небольшую `depth` и предел выборки. Проверять количество запросов при увеличении числа моделей, исключить запрос на каждый артикул.
- В расчёте проверять вход и подготавливать сегменты один раз на версию кривой. Для девяти моделей начать с простой реализации. Добавлять кэш, индекс, фоновую задачу или worker только при измеренном узком месте. Ключи кэша должны учитывать версию данных и границу публичного доступа.
- Основной экран загружает форму и результаты. Подробные кривые и лист данных загружать при открытии соответствующего блока. Тяжёлые библиотеки для экспорта подключать по требованию. Сначала проверить, достаточно ли существующих SVG и печатного шаблона.
- Сравнивать в одинаковых условиях время ответа сервера, количество запросов, размер передаваемых данных и время обновления результата в браузере. Фиксировать базовый замер и результат после изменения. Проверять как девять HIP 32, так и увеличенный тестовый набор перед расширением ассортимента.

## Интеграция с HEISSKRAFT

- Сохранять маршрут `/selection/pumps`, общую навигацию, дизайн и обёртку CMS. При подключении проверить, как редакторское переопределение страницы влияет на доступность программы. Наличие подборщика не должно требовать изменения маршрутов карточек или выдачи каталога.
- Локальный снимок предназначен для тестов. Публичная версия читает только опубликованные записи подбора с кривой нужного режима. Учитывать проверку инженерных данных и флаг `hydraulicsOnly`: публикация Q–H сама по себе не разрешает вывод полного листа данных.
- Публичный контракт определять белым списком. Отдавать артикул, имя, согласованные характеристики и расчётный результат. Черновики, служебные заметки, локальные источники, закрытые вложения и CMS-объекты целиком не включать. Проверять обе стороны связи по статусу и режиму. Для публичного вызова Payload явно задавать `draft: false` и `overrideAccess: false`. Если существующие права скрывают `pumpSelection`, спроектировать отдельную утверждаемую публичную проекцию с тестами доступа до интеграции.
- Данные редактора, предпросмотр и публичный ответ держать в отдельных потоках. Общий кэш допустим только для опубликованной проекции. После публикации, снятия с публикации и смены версии проверить, как обновляются результаты и листы данных.
- В публичном интерфейсе различать «нет подходящих насосов», «нет опубликованных данных» и ошибку сервиса. На графике подписывать единицы и оси, показывать границу рабочей зоны и значения выбранной точки текстом. Учесть клавиатуру, узкий экран и доступность кривых помимо цвета.
- PDF строить по тем же данным и результату расчёта. Показывать режим, артикул и исходные условия. КПД и напор могут быть на общем графике со своими шкалами. P2 и NPSHr показывать по доступным данным. Сохранять читаемость при печати и обозначать приближённые значения.

## Проверки перед объединением веток

1. В тестах расчёта покрыть точное попадание в узел, интерполяцию, нижнюю и верхнюю границы, превышение рабочего интервала, некорректный ввод и отсутствие вспомогательных рядов. Начать с 77005423 при Q = 8 м³/ч и H = 8 м. Проверить Q = 4, Q < 4 и Q = 9,4, где для этого артикула заканчиваются доступные числовые данные раньше каталожной границы.
2. Для интеграции проверить опубликованную запись подбора с более новым черновиком, снятие с подбора и расчёт при скрытой товарной карточке, ограничение `hydraulicsOnly` и отсутствие закрытых полей в публичном ответе. Для интерфейса проверить форму, объяснение результата, график, пустую выдачу и маршрут при отключённой CMS.
3. Выполнить `npm run typecheck`, ESLint по затронутым файлам и профильные тесты Vitest. После подключения страницы проверить используемую сборку сайта и сценарий в браузере. Если затронут контракт Payload, выполнить интеграционные проверки на отдельной базе разработки.
4. Работать с отдельными БД, секретами и медиахранилищем. Фикстуру использовать в расчётных тестах, без автоматического импорта при запуске. В Git сохранять только разрешённые данные и исходный код. При необходимости миграции описать эффект, подготовить резервную копию и порядок отката.
5. Перед переносом на сайт зафиксировать подтверждённые источники, проверенные артикулы, известные пробелы и замеры. Разделять расчёт, UI и CMS-интеграцию по проверяемым изменениям, чтобы любую часть можно было откатить отдельно.
